> **Estado:** versión final del Cierre (25/11/2026) · **Autora:** Evelyn (PO) · **Revisa:** Orlando · **Fuente:** [02 §2.2](../plan/02_mapeo_plantilla.md) (4.6.4), [04 §4.4](../plan/04_scrum_pmbok.md) (HU-28 y HU-22) · **Requisitos:** RNF008

> Las mediciones son de una PC con Docker Desktop y datos de demostración; sirven para **comparar** el antes y el después, no como valores absolutos de producción.

## Qué se midió y cómo

Se usó **Lighthouse 12** (modo escritorio, solo la categoría *Performance*) en tres vistas, con la sesión del jefe de ventas para las dos que requieren inicio de sesión:

| Vista | URL | Sesión |
|---|---|---|
| Login | `/web/login` | No |
| Backend | `/odoo/action-sale.action_orders` (pedidos de venta) | Jefe de ventas |
| Dashboard | `/odoo/action-spreadsheet_dashboard.ir_actions_dashboard_action` (Ventas, con los datos de demostración) | Jefe de ventas |

Cada vista se midió **3 veces** y se informa la **mediana**. El script es [`scripts/perf/lighthouse.py`](../../scripts/perf/lighthouse.py) (Lighthouse y Chromium corren en Docker, sin instalar nada en el PC); los resultados crudos están en [los resultados de Lighthouse](../capturas/sprint-3/HU-28_lighthouse_resultados.csv).

- **Antes:** el entorno de desarrollo (`docker compose up -d`, puerto 8069): Odoo sin Nginx, sin compresión ni caché y con `?debug=assets`, que sirve los archivos JavaScript y CSS sin empaquetar ni minificar.
- **Después:** el despliegue protegido de HU-27 (`scripts/levantar_prod.sh`, puerto 8443): Nginx con TLS, gzip y caché de assets, y Odoo con 2 *workers* y modo proxy.

## El tablero propio de M4 (HU-22)

Con M4 (`donofrio_tablero`, tag [`v1.4.0`](https://github.com/orlando572/erp-donofrio/releases/tag/v1.4.0)) se repitió la medición para el **tablero OWL** y para el login con la marca, con el mismo método de la HU-28 («antes» = desarrollo con `?debug=assets`; «después» = despliegue protegido con Nginx, TLS y gzip) y 3 corridas por vista (mediana). Se hizo el 24/11/2026 en otra PC (Linux, `--network host`), así que **no es directamente comparable** con la tabla anterior. El script es [`S4_lighthouse_m4.py`](../capturas/sprint-4/S4_lighthouse_m4.py) y los datos crudos están en [los resultados de Lighthouse de M4](../capturas/sprint-4/S4_lighthouse_m4_resultados.csv).

| **Login con la marca** | Escritorio | 98 | **100** | 0.38 | 14 | Sí |
| Login con la marca | Móvil | — | **95** | 1.68 | 238 | Sí |

El «después» del tablero se midió con el usuario Jefe de Almacén, porque el Gerente General exige 2FA. Las tres corridas de escritorio dieron 76, 76 y 81: solo una superó el umbral, así que el resultado no es estable.

> **Límite conocido (declarado).** El tablero propio saca **76 en escritorio** (meta: 80) y **39 en móvil** (Lighthouse emula un CPU 4 veces más lento). Sí cumple la parte de **carga en menos de 3 s**: LCP de **2.11 s**. Lo que frena el puntaje es el *Speed Index* (2.97 s) y, en móvil, el JavaScript del cliente web de Odoo, que bloquea el hilo principal 680 ms. Es la misma causa que el **59 del backend** y, como aquel, se declara como **límite conocido** y no como defecto del código del equipo: el componente OWL del tablero solo hace una llamada al servidor (`get_kpis`, entre 30 y 57 ms) y no se corrigió con configuración. RNF008 queda **Parcial**.

## Lectura frente a RNF008

RNF008 pide que el tablero cargue en menos de 3 s y un puntaje de rendimiento de al menos 80 en el login.

| Criterio | Resultado | Cumple |
|---|---|---|
| Rendimiento ≥ 80 en el login | 100 | Sí |
| Tablero en < 3 s (LCP) | 1.9 s | Sí |
| Rendimiento ≥ 80 en el dashboard | 80 | Sí (justo) |
| Rendimiento ≥ 80 en el backend | 59 | **No** (límite conocido) |
| Tablero propio (M4) en < 3 s (LCP) | 2.11 s | Sí |
| Rendimiento ≥ 80 en el tablero propio (escritorio) | 76 | **No** (límite conocido) |

**El backend queda en 59** aunque su LCP baja a 2.2 s: el problema que queda es el TBT (384 ms), que es el tiempo que el navegador tarda en ejecutar el JavaScript del cliente web de Odoo. Es el costo del propio framework y no se corrige con configuración; solo se reduciría con menos código en la página, algo que no se hace en el núcleo de la Fase 1. Se declara como **límite conocido**: lo explica el JavaScript de Odoo y no el código del equipo.

## Qué produjo la mejora

La comparación junta dos cambios, como pide el plan, y **no los separa**:

1. **Quitar `debug=assets`.** Con él, Odoo envía entre 14 y 19 MB de JavaScript y CSS sin empaquetar; sin él, los empaqueta y minifica. Es lo que más pesa en el backend y el dashboard.
2. **Nginx con gzip y caché de assets**, más los 2 *workers* de Odoo. El login baja de 4.1 MB a 0.6 MB transferidos.

Lo que se recomienda para el despliegue ya está hecho en HU-27: nunca servir con `debug=assets`, comprimir con gzip y dejar los assets en caché del navegador.

## Limitaciones

- Una sola PC, con Docker Desktop y sin red real: Lighthouse simula la red y la CPU, así que los segundos son una referencia comparativa.
- Certificado TLS autofirmado y sin CDN.
- Tres corridas por vista (mediana); la variación entre corridas fue pequeña (por ejemplo, el LCP del dashboard varió menos de 0.1 s).
- Los datos son los de demostración (16 semanas); con más datos el backend y el dashboard cargarían más filas.
- La medición del tablero propio de M4 se hizo en otra PC y con otro usuario (Jefe de Almacén), por lo que no se compara punto a punto con la del backend y el dashboard estándar. El puntaje móvil (39) es el del perfil emulado de Lighthouse.

## Cómo repetirlo

```bash
# Antes: entorno de desarrollo, con los datos de demostración cargados
python3 scripts/perf/lighthouse.py ANTES http://host.docker.internal:8069 --debug-assets
# Después: despliegue protegido (pide ODOO_ADMIN_PASSWD de 16 caracteres o más en el entorno)
scripts/levantar_prod.sh
python3 scripts/perf/lighthouse.py DESPUES https://host.docker.internal:8443
# Volver a desarrollo
docker compose --profile proxy down && docker compose up -d
```
